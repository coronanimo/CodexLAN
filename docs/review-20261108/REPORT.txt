CodexLAN 新旧架构代码审查
2026-11-08

处理进度：下文 R1 至 R7 已修改并部署到正式版 0.8.0-20261108-154715。后端 95 项、前端 55 项检查和发行包隔离 HTTP 检查通过。旧版已归档，新版使用 CodexLAN 正式目录。下文保留问题发现时的原因、复现结果和整体审查尚未覆盖的范围。

新版已经解决了旧版的一部分结构问题：输入框减少了同步计算布局的操作，长对话按屏幕附近的内容显示，服务端也不再依赖浏览器脚本。

目前发现的主要问题是：运行中的命令输出少了一道恢复保护；“复制原文”会改动代码里的文字；长回复可能停在生成到一半的画面；调整队列顺序可能让消息一直等着。另有已完成任务的缓存无法随分页读取释放、思考摘要不自动展开的问题。

这是一轮核心模块的审查结果。整体代码树的深度审查还没做完，剩余范围列在文末。

一、旧版和新版到底改了什么

比较的是重构前的 4b7814b，与 f6bf62c 加审查时工作区里的全部修改，包括新增文件。

旧版的主要逻辑集中在 public/app.js 和 server/conversations.mjs。前者同时处理网络、页面、输入和预览；后者同时处理原生协议、命令、队列和历史。改一个功能，经常要顾及同一个大文件里的其他行为。

新版把这些工作拆开：目录由 WorkspaceController 管，当前对话的读取由 ConversationReader 管，输入草稿留在编辑器里。服务端把 HTTP 和队列放进 core，把 Codex 协议放进 agents/codex。

这些修改带来了三项具体改善：

  1. 旧输入框每次调整高度都会先修改样式，再读取 scrollHeight。
     新版用 CSS 镜像撑开高度，减少了打字时强制计算布局的操作。

  2. 新时间线只挂载屏幕附近的消息和执行记录。
     一个任务即使有很多次命令，也可以逐条显示和读取详情。

  3. 服务端的存储和协议处理不再导入 public/ 下的浏览器代码。
     后续修改页面时，牵动服务端的机会更少。

下面的问题也与拆分有关。列表只存短摘要，完整正文单独读取，二者需要保持同步；历史改成分页后，旧有的缓存释放条件也需要跟着改。这些地方目前没有接完整。

二、已经复现的问题

R1  命令还没结束时，输出没有保存到本地恢复记录

命令运行过程中，页面已经显示的输出，新版只留在内存里。它会在命令开始和完成时保存快照，中间陆续收到的输出没有写进恢复记录。

如果服务在命令结束前退出，而 Codex 自己的历史也缺少这段输出，重启后就缺少可用于找回它的本地副本。旧版会分批保存运行中的输出，新版遗漏了这一步。这项应优先修复。

复现时，向新版适配器依次发送“命令开始、输出一段文字、断线”。存储接口只收到命令开始时的一次写入，里面没有输出文字。

修复时应恢复分批保存输出，并在正常关闭前处理待写内容。下一步验证是重载存储，检查中断前的文字能否找回，以及 Codex 后来补齐历史时是否会重复显示。

代码：server/agents/codex/adapter.mjs:63
      server/agents/codex/native-projection.mjs:80
旧版：4b7814b 的 server/conversations.mjs:1802


R2  已经读过的命令输出仍留在服务端内存里

新版分批读取历史，通常一次取 50 条命令。但释放实时缓存的条件仍要求一次读取包含整个任务的全部条目。分多页读完后，它没有记住前面几页已经核对过。

复现中，一个已完成任务有 120 条命令，按 50、50、20 条全部读完后，120 条仍留在缓存里，合计约 786 万个输出字符。实际内存占用还需要测量。

这会让长任务的缓存迟迟释放不了。单条输出有长度限制，任务数和条目总数却没有相应限制，长时间运行时存在内存持续增加的风险。

修复时需要记录每条命令是否已经在历史中找到，逐步释放已经核对的内容。尚未进入历史的输出则应先保存到恢复记录。这个修改需要和 R1 一起处理。

代码：server/agents/codex/native-projection.mjs:161
      server/agents/codex/history.mjs:167
      server/agents/codex/adapter.mjs:59


R3  “复制原文”会改掉代码示例里的字符串

例如回复里有这样一行代码：

  const example = "[manual](docs/manual.md)";

新版正文接口返回的却是：

  const example = "manual";

原因是文件卡片的解析程序扫描了整篇回复，把代码块里的链接字符串也当成文件引用处理。新版又把处理后的文字提供给“复制原文”、分享和 PDF，导致这些功能拿到的内容已经变化。

旧版也有显示时误识别文件引用的问题，但复制按钮读取的是另外保留的原文。新版把影响扩大到了复制内容。

复现已调用实际正文读取代码，返回的就是上面被改动的字符串。这项应优先修复，复制代码时尤其容易造成误用。

修复时应保留原文供复制和导出使用；生成文件卡片时跳过代码块、行内代码和转义内容。

代码：server/agents/codex/content-references.mjs:32
      server/agents/codex/history.mjs:376
      web/src/features/details/ResourceActions.tsx:20
旧版：4b7814b 的 public/app.js:2516


R4  回复超过 12,000 字符后，生成中的画面可能不再继续更新

新版列表只保留前 12,000 个字符，完整回复通过另一个接口读取。达到这个长度后，服务端会直接跳过后续文字增量，同时停止发出这条消息的更新通知。

前端依靠这些通知重新读取完整回复，因此长回复仍在生成时，画面可能停住；完成事件到来或重新读取后，最终内容可能补齐。

复现中，先让回复超过上限，再追加文字，后续更新事件为零，消息的版本号也没有变化。

修复时可以继续限制列表摘要的长度，同时定期通知前端读取新增正文。下一步应把超过上限、继续生成和最终完成连起来做一次页面验证。

代码：server/agents/codex/native-projection.mjs:76
      web/src/features/details/MessageContent.tsx:16


R5  在特定时机调整队列顺序，会让消息卡在队列里

过程如下：

  1. 系统正在检查第一条消息能否发送。
  2. 此时把第二条消息移到最前面。
  3. 检查结束，系统发现第一条变了，于是退出这次发送。
  4. 调序操作没有重新启动发送，队列就停住了。

复现后，队列顺序已变成第二条在前，两条消息都还在等待，发送次数为零，后台也没有待执行的发送任务。之后的新提交或其他事件可能重新启动它。

原因是队列操作和后台发送共用同一份队列，调序只更新了列表，没有让后台重新检查新队首。

修复时，修改队列顺序后应重新检查发送条件；移动消息时也要检查被交换的另一条是否正在提交。验收要确认按新顺序发送，并且每条只发一次。

代码：server/core/queue-coordinator.mjs:27、45、77


R6  思考摘要已经到达，标题仍停在“整理思路”，也不自动展开

思考开始时，第一条事件可能没有摘要文字，页面先生成一个折叠的“整理思路”条目。后面摘要陆续到达，服务端只通知正文变化，没有更新标题和展开状态。

因此手动打开的正文可以更新，尚未打开的条目却继续折叠，标题也可能一直不变。

复现中，摘要增量到达后只产生正文更新通知，没有产生标题和自动展开状态的更新。

修复时，在第一段摘要到达、标题发生变化时更新这几个显示字段，正文继续按需读取。

代码：server/agents/codex/native-projection.mjs:85
      server/agents/codex/presentation.mjs:45
      web/src/features/details/useDetailPage.ts:30


三、还需要在浏览器里确认的问题

R7  对话达到显示上限后，页面可能停止更新，却没有明显的恢复按钮

前端最多保留 1,500 条记录或约 2 MB 的展示内容。达到上限后会暂停接收后续显示更新，并生成“点击最新记录继续”的提示。

这段提示目前只被放进全局设置中的连接状态。“回到最新”按钮则只在用户离开底部时出现。如果用户一直在底部跟随输出，就可能既看不到提示，也看不到按钮。

这是从代码中发现的操作缺口，还没在浏览器中实际触发。需要构造达到上限的对话，检查底部阅读和上翻阅读两种情况。若画面与代码所示一致，应在暂停时直接显示原因和恢复按钮。

四、其他值得处理的地方

远程文件预览仍会整份下载。

打开服务器上的日志、JSON 或源码文件时，前端先下载整份文件，再转成字符串并显示。本地待上传文件有 200 KB 预览限制，远程预览没有使用这个限制。旧版也存在这个问题。大文件会增加下载时间和浏览器内存占用，建议为预览设置大小限制，完整文件保留下载入口。

代码：web/src/transport/file-client.ts:17
      web/src/features/content/PreviewHost.tsx:32、60

部分旧会话的目录读取可能需要扫描整个会话列表。

目录缓存没有命中时，storedMetadata 会逐页查找原生会话；缓存最多保留 2,048 项。大量会话下的耗时尚未测量，后续应针对这个读取过程测一次。

代码：server/agents/codex/catalog.mjs，storedMetadata

服务端适配器的接口声明尚未检查实际实现。

项目声明了 AgentAdapter 接口，但当前类型检查只检查声明文件，实际的 .mjs 实现没有参加类型检查。以后增加代理时，方法参数或返回值写错，仍可能到运行时才发现。建议让适配器实现也接受类型检查。

代码：server/agents/adapter-contract.ts
      web/tsconfig.json

多提供者还需要继续开发。

目前实际运行的是 codex-local。会话绑定没有提供者实例字段，命令还要求 UUID 格式的会话 ID。接入使用其他 ID 的代理时，需要增加 ID 映射和绑定信息。


五、权限、数据和发布检查结果

本轮检查了新 HTTP 路由的项目授权、会话归属，以及读取过程中撤销权限的处理。项目权限变更和账号会话撤销会关闭持续连接；文件读取继续检查真实路径。相关隔离 HTTP 测试通过。

队列新增了“正在提交、明确拒绝、结果不确定”等记录。超时后保留不确定状态，等待核对，可以减少自动重发造成的重复执行。队列调序与后台发送的配合仍有 R5 的问题。

数据库结构文件 workspace-database.mjs 与旧版一致。队列、附件、设置和恢复记录的写入方式发生了变化。现有存储重载和迁移测试通过，运行中输出的恢复写入缺口见 R1。

发布改为构建 React 静态文件，再由 Node 服务提供。构建缺失时返回明确错误。并行安装使用独立数据副本，并排除原版正在使用的队列和登录会话；更新脚本支持切回上一份发布包。
